# Operations

## Configuration

`config.yaml` is loaded through bconfig, followed by `APP__` environment overrides. Double underscores denote path separators and preserve underscores inside keys. For example, `APP__DB__POSTGRES__PASSWORD` and `APP__SECURITY__ENCRYPTION_KEY`.

Local credentials are generated by `scripts/configure.py`. Do not regenerate the encryption key for an existing database. Back up `.env` securely and back up PostgreSQL with your established database backup process. Restore both together in an isolated environment before relying on backups.

The supplied images are pinned to exact versions and all Compose services have health checks and CPU/memory limits. Platform and worker run without root, with read-only filesystems and dropped Linux capabilities. The PostgreSQL volume persists across container replacement.

## Connect external plugins

Set `PLUGIN_ALLOWED_HOSTS` in `.env` to a comma-separated list of exact hosts, such as your Vault, Consul, model, MCP, One Data, and external database hosts. Recreate the worker after changes. No wildcard host allowance is provided by the SDK.

For bootstrap credentials, add `PLUGIN_SECRET_...` environment variables only to the worker's Compose environment using your deployment secret mechanism. Then use the Environment secret plugin with the variable's name. Connect its output to the Vault/Consul/service credential input. Do not expose platform credentials to the worker. Alternatively, the Static credential plugin accepts a directly entered value, stores it in encrypted revision configuration, and emits a sensitive output.

TLS verification is enabled by HTTP clients. Mount your enterprise CA bundle into the worker and configure the appropriate trust store when using an internal CA. PostgreSQL memory defaults to `verify-full`; `disable` is intended only for controlled local environments.

## Keycloak

The Compose deployment runs Keycloak 26.7.3 with a dedicated PostgreSQL database. Traefik exposes it only through the application's `/identity` path; Keycloak has no published host port. Its built-in `master` realm receives the generated bootstrap administrator. The declarative `deployments/keycloak/app-builder-realm.json` import creates the application realm, OIDC client, Forma login theme, roles, and `brian` editor account whenever the Keycloak database is new. Startup import skips an existing realm, preserving runtime changes across ordinary restarts.

`scripts/configure.py` detects the local Tailscale MagicDNS hostname and stores it as `APP_PUBLIC_HOST`. It also generates independent Keycloak database, bootstrap administrator, OIDC client, and `brian` passwords. Existing `.env` values are retained and only missing settings are appended.

The platform receives these OIDC settings from Compose:

- `APP__OIDC__ISSUER`: externally reachable realm issuer.
- `APP__OIDC__CLIENT_ID`: registered client ID.
- `APP__OIDC__CLIENT_SECRET`: client secret.
- `APP__OIDC__REDIRECT_URL`: public origin plus `/auth/callback`.
- `APP__SECURITY__SECURE_COOKIES=true` when served through HTTPS.

Realm roles `workflow-admin`, `workflow-editor`, and `workflow-viewer` are included in ID-token `realm_access.roles`. Authorization uses BAccess predicates. Login uses OIDC verification and PKCE; state is bound to an encrypted, short-lived HTTP-only cookie. Sessions expire after eight hours. The local operator bearer token remains an administrative API credential when configured; remove it if only OIDC authentication should be permitted.

Traefik binds the single application port to all host interfaces for Tailscale access; the platform, Keycloak, databases, worker, Consul, and collector remain private or loopback-bound. Tailscale provides encrypted transport for this local HTTP deployment. For access outside the tailnet, configure Traefik with TLS, secure cookies, a trusted OIDC origin, network policy, collector backend, backups, and production secret delivery.

## Telemetry

Go uses BTelemetry OTLP/gRPC for traces and metrics and the OpenTelemetry slog bridge for OTLP logs. Python uses OTLP/HTTP for all three signals. Both point at the Collector. Go-to-Python trace context uses W3C `traceparent` and `tracestate`.

Core labels include workflow name, plugin name, and plugin version. Logs/traces also carry workflow ID/revision, run ID, node ID/name, and attempt. Custom metrics are declared in the manifest; the SDK fixes their context labels to avoid per-run series. Workflow-level log field opt-ins are saved in revisions.

The checked-in collector uses its debug exporter for local verification. Replace it with the organization's OTLP backend or separate logs/metrics/traces exporters. Set retention outside the application; this release does not automatically prune encrypted runs, history, or audit events.

## HTTP API

Requests use an authenticated session cookie or the operator bearer token. JSON mutations are limited to 2 MiB. Inbound hooks use their own one-time-issued bearer token.

| Method/path | Operation |
| --- | --- |
| `GET /api/plugins` | Installed immutable manifests |
| `GET, POST /api/workflows` | List/create workflows |
| `GET, PUT /api/workflows/{id}` | Read/save; save includes expected `base` revision |
| `GET /api/workflows/{id}/history` | Latest 200 revision snapshots |
| `POST /api/workflows/{id}/restore` | `revision`, expected `base`, optional `nodeId` |
| `POST /api/workflows/{id}/publish` | Publish expected `base` revision |
| `GET, POST /api/workflows/{id}/runs` | List latest 100 runs/enqueue with JSON `input` |
| `GET /api/runs/{id}/steps` | Step state without secret payloads |
| `POST /api/runs/{id}/cancel` | Cancel a queued or active run |
| `GET, POST /api/workflows/{id}/bindings` | Create binding for `nodeId` with `mode` (`draft` or `published`); admin only |
| `POST /hooks/{id}` | Authenticated JSON event; HTTP 202 response with run ID |

`Idempotency-Key` on run creation/hooks deduplicates within a workflow. Reusing a key returns the original run; callers must not reuse it for different payloads. Node restore restores configuration/plugin version/position for a node that exists in both revisions; it retains current connections and validates compatibility.

## Verification status

Automated unit/integration/E2E tests are intentionally pending the repository owner's required approval. Compile/lint and local execution checks are performed during implementation. Real on-premises endpoints and organization-specific authentication must be verified with actual service configuration; they are not simulated as successful integrations.
