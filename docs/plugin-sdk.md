# Plugin SDK

The application contains no integration registry switch, provider list, or provider-specific form. Installed manifests define the catalog. The Go platform uses `sdk/go/plugin` as its wire contract. Python plugin authors use `workflow_sdk.Context`; new resource types and providers do not require changes to the platform.

## Package lifecycle

A plugin directory contains `manifest.json`, `plugin.py`, and optional immutable supporting files. The package name is namespaced, such as `team.customer-lookup`. The version is an exact `major.minor.patch`. Directories may use any name, so `customer-lookup-1.0.0` and `customer-lookup-2.0.0` can coexist. Install both into platform and worker images. Never replace a registered name/version with different contents.

1. Run `uv run --project python workflow-plugin new team.customer-lookup` from the repository root.
2. Implement `async execute(ctx)` and declare its configuration, inputs, outputs, diagnostics, permissions, and custom metrics in the manifest.
3. Add required third-party packages to `python/pyproject.toml`, then run `uv lock --project python`. All installed plugins currently share that locked Python environment. Use a separate worker deployment when dependency sets or trust boundaries differ.
4. Run `uv run --project python workflow-plugin seal --root plugins` after finishing the package. The digest covers manifest semantics and all package files except generated bytecode and the manifest's own digest field.
5. Run `uv run --project python workflow-plugin validate --root plugins`.
6. Rebuild with `docker compose up -d --build`. Startup registers new immutable versions in PostgreSQL. A changed registered version fails startup. Retain old artifacts for historical workflow execution.
7. Add the new component to a workflow. The node stores its exact plugin version. Upgrade deliberately by replacing or editing the node through the workflow API, then save a new revision and publish when ready.

The scaffold is an executable identity transform, not an unimplemented handler. Evolve it into the desired behavior before installing it.

## Manifest contract

The machine-readable standard is [`manifest.schema.json`](../python/workflow_sdk/manifest.schema.json). The CLI validates manifests against it before loading packages. JSON Schema checks are supplemented by duplicate-port and schema-compilation checks.

| Field | Meaning |
| --- | --- |
| `protocol` | `workflow.plugin/v1`; incompatible protocol versions are rejected |
| `name`, `version`, `digest` | Stable identity, exact release, and SHA-256 artifact integrity |
| `title`, `description`, `category` | Catalog and inspector presentation |
| `kind` | `action`, `resource`, or `trigger` |
| `configSchema` | JSON Schema for immutable node settings; include defaults for editor creation |
| `inputs`, `outputs` | Named ports with title, schema, kind, required flag, and sensitivity |
| `resourceType` | Exact resource contract identifier on resource ports, such as `ai.chat-model/v1` |
| `permissions` | Declared SDK capabilities; current helpers support `network.http`, `network.postgres`, and `secrets.environment` |
| `logFields` | Payload field names that workflow creators may opt into logging |
| `metrics` | Declared instruments with name, counter/histogram kind, unit, and description |

Schemas are validated at registration, before invocation, and after results return. Unknown outputs are rejected. The canvas checks coarse port compatibility; the server checks graph structure and runtime values against full JSON Schema. The system does not claim to prove arbitrary JSON Schema assignability statically.

The generic inspector currently renders top-level strings, numbers, booleans, enums, and structured JSON. Complex schema values are editable as JSON. Adding a resource type requires a new `resourceType` identifier and compatible producer/consumer plugins, not application changes.

## Execution context

| SDK API | Behavior |
| --- | --- |
| `ctx.config` | Validated saved configuration |
| `ctx.inputs` | Validated upstream results; resolved secrets are available only inside execution |
| `ctx.execution` | Workflow ID/name/revision, run ID, node ID/name, attempt, W3C trace context |
| `ctx.idempotency_key` | Stable `run-id:node-id` across retries; pass to side-effecting services |
| `ctx.log(event, level='info', **fields)` | Structured correlated log; optional fields require manifest declaration and workflow opt-in |
| `ctx.span(name)` | Context manager creating a child span with workflow/plugin metadata |
| `ctx.metric(name, value)` | Record a declared counter or histogram with bounded workflow/plugin labels |
| `await ctx.http(method, url, ...)` | Timed HTTP helper with host allowlist, response-size cap, redirect rejection, and tracing |
| `ctx.environment_secret(name)` | Resolve an operator-provisioned `PLUGIN_SECRET_...` variable |
| `ctx.resource(type, value)` | Produce a versioned, digest-pinned resource descriptor |
| `ctx.resolve(descriptor)` | Async context manager that imports the producer's resource hook and ensures cleanup |

Raise `PluginError('stable_error_code', retryable=True)` only for failures safe to retry. The engine persists the error code rather than arbitrary exception text, which may contain credentials or response data. Runtime exceptions default to a non-retryable generic failure. Never place secrets into exception codes, span names, or log event names.

The runtime sets up OpenTelemetry providers and exporters. Authors do not initialize their own exporters. Custom metric names must be declared; invocation-specific IDs are kept out of metric labels. Names are labels and can still create new series when renamed, so use stable workflow naming conventions. Full identifiers remain on traces and logs.

Sensitive input strings and configuration properties marked `writeOnly` are redacted by the SDK logger, including nested values. Keep event names constant. Only log payload fields whose contents you have reviewed; redaction is not a general data-loss-prevention system. Avoid logging raw prompts, tool results, connection strings, or external response bodies. Ordinary stdout/stderr from plugins is discarded; use `ctx.log` for exported diagnostics.

## Resource composition

Resource values are serializable descriptors. Live Python connections and model instances never cross the wire. A producer returns `ctx.resource(type, value)`; the receiving plugin uses `async with ctx.resolve(...)`. The runtime looks up the exact producer artifact and calls its `open_resource(ctx, value)` async context manager.

This enables independently supplied model wrappers, MCP tools, and memory implementations. A custom model plugin can construct any compatible LangChain chat model, including a wrapper for a non-OpenAI protocol, and yield it through `ai.chat-model/v1`. The application and agent plugin need no provider-specific branching.

Current resource contracts:

| Contract | Resolved value |
| --- | --- |
| `ai.chat-model/v1` | LangChain chat model accepted by `create_agent` |
| `ai.tools/v1` | List of LangChain-compatible tools |
| `memory.checkpointer/v1` | Async LangGraph checkpointer |

Provider resolution gets its own plugin logging identity while retaining the consuming node's execution context. Resources are reopened with async cleanup for each invocation. On retry, resource producer steps resolve again; successful action steps are reused from encrypted checkpoints.

For PostgreSQL memory, connect explicit host, port, database, username, and password inputs. Configure TLS and namespace on the memory node. Initialization is an explicit switch because checkpointer setup creates tables in the chosen external database. The runtime never receives the platform database password or encryption key. Memory conversation IDs combine workflow ID, namespace, and the configured thread ID; an empty thread ID uses the run ID.

## OpenAPI / One Data

One Data is implemented by the `community.openapi-operation` plugin and the SDK's package importer. It is not a platform integration.

Use a local JSON OpenAPI document:

```sh
uv run --project python workflow-plugin import-openapi /absolute/path/service.openapi.json \
  --operation createCustomer \
  --name company.create-customer \
  --base-url https://services.internal \
  --root plugins
```

This produces a sealed plugin with named input ports and pinned operation code. Multiple plugins can use the same origin and different paths. Acyclic local `$ref` values are expanded. External and recursive references are rejected. The importer currently supports OpenAPI 3.x JSON, scalar path/query/header parameters, JSON request bodies, and optional bearer authentication. Unsupported parameter serialization fails import rather than silently producing an incorrect request. Other authentication and media types belong in the generated plugin's implementation.

## Trust and deployment

Installed plugins are operator-reviewed executable code. A subprocess is an execution boundary, not a sandbox for hostile code. SDK capability declarations and HTTP allowlists protect cooperative plugins; arbitrary Python code can bypass SDK helpers. The worker runs as a non-root user in a read-only container without platform credentials. Deploy separate workers and enforce network policy at the container/network layer for different trust domains.

The HTTP worker runs at most four child processes and enforces a 120-second invocation timeout. The Go scheduler currently executes one workflow at a time per platform replica. Multiple replicas share PostgreSQL job claiming and fencing tokens. Long-running external tasks should return durable job references through a custom plugin; the first release does not provide indefinite sleeps or interactive agent pauses.

## Compatibility and boundaries

- One trigger per workflow; manual runs may supply its event input.
- Acyclic dependency graphs with deterministic joins: all connected upstream nodes must succeed.
- No arbitrary cycles, implicit branching, or embedded code evaluation in the platform.
- Trigger bindings accept authenticated JSON POSTs and return HTTP 202 with a run ID. Custom synchronous response mapping is not yet supported.
- Cancellation stops scheduling and cancels the caller's wait; a remote invocation already in progress can finish or reach its timeout. Completed external effects are not undone.
- Exactly-once external side effects are not promised. Endpoints must honor idempotency or plugins must reconcile uncertain outcomes.
- Plugin signatures, per-package dependency environments, a visual code editor, and a marketplace are not implemented. Artifact digests enforce consistency, not publisher identity.

## Static credentials

Use `community.static-secret` to enter a credential directly. Its manifest marks the configuration field `writeOnly`, which produces a masked input, and marks the output sensitive. New revision configurations are encrypted by the platform independently of plugin kind. The API returns decrypted configuration to authorized workspace readers; do not grant workspace access to people who should not read its credentials. For centrally managed rotation, use Vault or an environment reference instead.

## Selecting resources and connecting multiple sources

Every input now has a source picker in **Inputs & resources**. It lists compatible output ports on existing nodes and compatible installed plugins to add. Selecting a new provider creates the node and connection together. **Configure** opens its settings; **Used by** returns to the consumer. The canvas also supports dragging between enlarged handles and a node selector for keyboard navigation.

A port may declare `multiple: true`. The engine then supplies an ordered array of values, ordered by saved edges, validating every item against that port's `schema`. Ports without this flag accept one source; selecting a replacement replaces only that input's connection. Duplicate edges and cycles are rejected. `community.langchain-agent@1.1.0` accepts multiple tool resources and combines their tool lists. Version 1.0.0 remains available for existing workflow history; the version picker makes upgrades explicit.

## Incoming webhook controls

The trigger inspector contains persistent **Test endpoint** and **Live endpoint** tabs. A test endpoint uses the latest saved draft. A live endpoint requires publication and uses the published revision. Both accept incoming authenticated JSON POSTs, return HTTP 202 with a run ID, and show their latest received run in the inspector. Tokens are encrypted at rest and available to administrators through the endpoint settings. Existing legacy endpoints continue to work; their original tokens cannot be recovered because only hashes were stored.

Use **Copy curl command** to POST from this machine to the local workflow. **Send test POST** exercises the same incoming endpoint from the browser. These controls do not invoke an outbound HTTP node. An invalid workflow is rejected before enqueueing; missing tokens receive HTTP 401, and non-POST methods receive HTTP 405.


## Exposing a workflow response

A workflow node may set `responsePort` to the name of one of its declared data outputs. This is workflow configuration, saved in every immutable revision; it does not add HTTP behavior to the plugin. At most one node may expose an output. Resource outputs cannot be exposed this way.

For an incoming webhook, the Go transport waits up to 50 seconds when the pinned workflow revision declares a response output. Completion returns HTTP 200 with `{ "runId": "…", "status": "succeeded", "response": <selected value>, "statusUrl": "…" }`. It returns only that selected output, never the full execution map or intermediate credential resources. A failed or cancelled run returns HTTP 422 with its status.

Pass `?wait=0` to enqueue without waiting. Pending runs, including those exceeding the wait deadline, return HTTP 202 with `Location`, `Retry-After`, and `statusUrl`. GET that URL with the same webhook bearer token to retrieve the result. The result is resolved from the run's original revision, even after a new workflow revision is published. Disconnecting an HTTP client does not cancel queued execution. Result responses disable caching.

## Port direction on the canvas

Each input/output port can declare optional `side`: `left`, `right`, `top`, or `bottom`. The renderer uses that plugin metadata without special cases for particular integrations. Omitted sides default to left for data inputs, right for data outputs, bottom for resource inputs, and top for resource outputs. Declaration order controls ordering along each side. Input/output semantics and port IDs remain unchanged when their positions change.

Data edges are solid with round ports; resource edges are dashed with square ports. Both have arrowheads pointing toward the consuming input. Newly created providers are placed toward the consumer input side. Side metadata is part of the sealed manifest, so changing it requires a new plugin version.
